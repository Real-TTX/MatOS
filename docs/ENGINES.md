# The engines: MatDock, Matcad, Matddns, MatIdentity, MatSMTP

MatOS is a layer **on top of** five programs. They are not catalog apps that happen to be installed; they are
the engines, and each of them **owns** one part of the configuration, so it is visible and editable in its own UI:

| Engine | Owns | MatOS uses it for |
|---|---|---|
| **MatDock** | stacks (compose + env), containers, backups, schedules, updates | install / update / start / stop / remove an app, its logs, its backups |
| **Matcad** | routes, certificates, DNS providers for certificates, logins | `app.example.com` for every app, wildcard certificates |
| **Matddns** | sources of the IP, DNS records, rules | the DNS record `app.example.com` that follows the home IP |
| **MatIdentity** | people, groups, the apps (OIDC clients) and who may open them | one sign-in for every app and for MatOS itself |
| **MatSMTP** | relay users, the accounts mail leaves through, rules, the queue | one relay user per app that sends mail, so all mail leaves through one place |

MatOS itself keeps only what no engine knows: users and sessions, shared links, the catalog, the wizard's choices, which
catalog entry an app came from, and where it sits on the home screen.

This page is the **contract**: what every engine offers to MatOS. All five speak the same small REST dialect. They are installed in the order of
`EngineIds.All`: MatDock (it deploys the others), Matcad, Matddns, MatIdentity, MatSMTP (registered in MatIdentity as it is deployed); all five are `core: true`.

## Common rules

- Base path **`/api/v1`**, JSON (camelCase), `Content-Type: application/json`.
- **Authentication:** the header **`X-Api-Key`**, compared in constant time with the key from the configuration. **No key
  configured = the API answers `503`** (`{"error":"..."}`), so it can never be reached unauthenticated. A wrong or missing key is `401`.
  The API ignores the session cookie.
- **Errors** are `{"error": "readable message"}` with `400` (invalid input), `404`, `409` (conflict) or `5xx`.
- **`GET /api/v1/status`** answers `{"ok": true, "app": "matdock|matcad|matddns|matidentity|matsmtp", "version": "<informational version>", "apiVersion": 1}`
  (plus whatever the engine already returned). MatOS uses `apiVersion` to know what it may call; it must not call an endpoint that a lower
  `apiVersion` does not have.
- **Idempotent writes:** `PUT` and the `POST` upserts can be repeated with the same body without a side effect.
- **`managedBy`:** every object that MatOS creates carries `"managedBy": "matos"` (a free string, stored, returned in lists). The engine's own UI
  shows a small badge on such objects, `Managed by <value>` (the engines name `mattiverse` *Mattiverse* and show any other value as it is, so
  MatOS's objects read **"Managed by matos"**; an object an install of Mattiverse wrote reads *Managed by Mattiverse* until MatOS writes it again),
  with the hint that the tool writes them and that manual changes may be overwritten. This is how a user who opens the engine sees where a setting came from.
- **Long operations** (MatDock only) are asynchronous: the request answers `202 {"operationId": "..."}` and the output is polled from
  `GET /api/v1/operations/{id}?offset=<chars already read>` →
  `{"id","kind","status":"running|succeeded|failed","output":"<new text>","offset":<next offset>,"finished":bool,"error":null|"text","result":{...}}`.
  Output that is produced only at the end is acceptable; streaming while it runs is better.
- The engine's key is generated by MatOS when it installs the engine and handed over as an environment variable (named below).
- **Shown in the window of MatOS:** every engine reads **`MAT_FRAME_ANCESTORS`** (MatDesign docs/PLATFORM.md, "Shown inside another app"): the origins of MatOS,
  separated by spaces. Set, its answers carry `frame-ancestors 'self' <origins>` and no `X-Frame-Options`, so MatOS can open the engine's own pages in the window
  of its home screen; unset, nobody may frame it (as before). MatOS fills it before each deploy of the engine (`FrameLink`). MatPlatform 1.5.0 does it
  (`MatFrameAncestors`, registered by `AddMatPlatform`; MatIdentity calls `AddMatFrameAncestors` itself); the engines carry that copy on their branch
  `feature/frame-ancestors` (2026-11-09).

## Matcad (`ghcr.io/real-ttx/matcad`)

Matcad already had the API (`/api/v1`: `status`, `provider-types`, `providers`, `authentications`, `routes`, `routes/manual`,
`certificates`, `settings`, key `Matcad__ApiKey`). MatOS needed these additions (all built, branch `mattiverse-integration`):

1. **`MATCAD_ADMIN_PASSWORD`** (environment): when no user exists, `admin` is created with this password, **without** the forced change, and
   the setup wizard is treated as completed. A value shorter than 8 characters or equal to `admin` is ignored with a warning (Matcad then seeds `admin`/`admin` with the forced change). Without the variable nothing changes.
2. **`PUT /api/v1/settings`** also accepts `"setupCompleted": true` (and returns it).
3. **`GET /healthz`** anonymous, plain `ok`.
4. **`/api/v1/status`** additionally returns `app`, `version`, `apiVersion`.
5. **`managedBy`** on routes, providers and authentications: accepted on `POST`, returned on `GET`, shown as the badge in the lists. A missing
   `managedBy` on an update keeps the stored value, `""` clears it.

Used: `GET/PUT /settings` (`baseDomain`, `setupCompleted`), `POST /routes` (upsert by `id`; **MatOS looks the id up by host first**, because a
`POST` without `id` always creates a new route), `DELETE /routes/{id}`, `POST /providers` (`{id?, name, type, credentials, managedBy}`).

**Certificates through the DNS challenge.** Matcad uses a DNS provider only for a **wildcard route**: one `*.domain` certificate, and the
single hosts below it (`app.domain`) are served from it; the `providerId` of a single host is ignored. So with a DNS account MatOS creates

```json
POST /routes  {"host": "*.apps.example.com", "wildcard": true, "providerId": 1, "target": "redirect",
               "fallbackUrl": "https://matos.apps.example.com", "enabled": true, "name": "MatOS wildcard", "managedBy": "matos"}
```

(other names on the wildcard lead to MatOS) and one single-host route per app with `target: "proxy"`. Without a DNS account only the single
hosts exist and Caddy uses the HTTP challenge (ports 80 and 443 must reach the host).

**Routes of the engines themselves.** Matcad's own UI (role `proxy`) is not published through itself; MatDock and Matddns are.

**Response headers (0.13.0, capability `responseHeaders` in `GET /status`).** `POST /routes` takes `responseHeaders: [{name, value}]` on a route: a value is
set on every answer and replaces the upstream's header as a whole (Caddy's deferred `set`), an empty value removes the header; the field missing keeps what the
route has, `[]` clears it. `GET routes/manual` shows them. MatOS uses it for **every app in the window** (docs/ARCHITECTURE.md): on the `web.route` binding of an
app whose compose file does not name `MAT_FRAME_ANCESTORS` and that sends no content security policy of its own, it writes the route back unchanged
(`MatcadClient.ResponseHeadersBody`: the fields of `routes/manual`, `managedBy: matos`; Matcad keeps the binding, the access fields and the options) with

```json
"responseHeaders": [{"name": "X-Frame-Options", "value": ""},
                    {"name": "Content-Security-Policy", "value": "frame-ancestors 'self' http://localhost:8030 http://127.0.0.1:8030 https://matos.example.com"}]
```

plus whatever else an administrator set there. Not on an older Matcad (it would ignore the field), not on a route with *Allow embedding*, not when the route has
a frame header of an administrator.

## Matddns (`ghcr.io/real-ttx/matddns`)

Matddns has no management API today (only the push endpoints `/api/update`, `/nic/update`, the monitoring `/api/health`, `/api/state`, and the
anonymous `/healthz`). New: the key is **`MATDDNS_API_KEY`** (environment, config `Matddns:ApiKey`) and the API manages exactly what the UI manages.
Ids are the existing 32-character hex ids. Validation is the same as in the UI. Every write is saved atomically and takes effect without a restart.

| Method and path | |
|---|---|
| `GET /api/v1/status` | as in the common rules, plus `counts: {sources, domains, rules}` |
| `GET /api/v1/sources`, `POST /api/v1/sources`, `DELETE /api/v1/sources/{id}` | `POST` is an **upsert** by `id`, else by `name` (case-insensitive). Body = the source as the UI saves it (`name`, `kind` = `PublicIp`/`Static`/`Dns`/`Push`/..., `intervalSeconds`, the kind's settings object, `entries`), plus `managedBy`. A new `PublicIp` source gets its entry like in the UI. Response = the stored source including all ids. |
| `GET /api/v1/domains`, `POST /api/v1/domains`, `DELETE /api/v1/domains/{id}` | A *domain group* is a provider account with its records: `name`, `kind` (`Cloudflare`/`Netcup`/`Hetzner`/`GoDaddy`/`DynDns`/...), the kind's settings object (credentials), `entries: [{id?, hostname, type: "A"|"AAAA"|"CNAME", recordName?, domain?}]`, `managedBy`. Upsert by `id`, else by `name`. **`entries` is the complete list** of the group (entries that are not in the body are removed, ids that are in it are kept), so MatOS can add and remove one host by sending the new list. Credentials are never returned (a `"credentialsSet": true` flag instead). |
| `GET /api/v1/rules`, `POST /api/v1/rules`, `DELETE /api/v1/rules/{id}` | Upsert by `id`, else by the pair (`domainGroupId`, `domainEntryId`). Body as in the UI: `enabled`, `onChange`, `intervalSeconds`, `validatePing`, `validateTcp`, `validationPort`, `domainGroupId`, `domainEntryId`, `sourceEntryIdsInOrder`, `managedBy`. |
| `POST /api/v1/run` | evaluates all rules now (like the periodic check); answers `{"ok":true}` |

The UI marks objects with `managedBy` with the badge ("Managed by matos", the value as it is) on the sources, domains and rules lists.

What was built, and where it differs from the sketch above (branch `mattiverse-integration`):

- **A record that a rule uses cannot be dropped.** `POST /domains` with a shorter `entries` list answers `409` naming the rule, and
  `DELETE /domains/{id}` is `409` while rules use the group. The API never deletes a rule as a side effect: MatOS deletes the rules of the
  records that leave first. (The UI still cascades.)
- `kind` is required on create and cannot change later; an interval of 1 to 14 seconds is a `400` (the UI clamps it); a CNAME on a DynDNS group is a `400`.
- Omitting `entries` on a group leaves its records alone, omitting credentials keeps the stored ones; secrets are never returned (`credentialsSet`).
- Without `domain` on a record the zone is guessed as the last two labels, which is wrong for `example.co.uk`: MatOS always sends
  `recordName` and `domain`. Credentials of a provider live in its settings object (`cloudflare`, `hetzner`, `netcup`, camelCase fields), `allowDynamic: true` lets
  Matddns create a record that does not exist yet.
- Deleting a source or one of its entries drops it from the failover lists of the rules, as in the UI. The UI's dynamic (pattern) rules are not part of the API.
- What MatOS writes for an own domain (docs/ARCHITECTURE.md "Domain and DNS"): one source at a time, `MatOS public IP` (`PublicIp`), `MatOS fixed IP`
  (`Static`, `static: {ip, ipv6}`, both sent so the other family is cleared) or `MatOS tunnel` (`Dns`, `dns: {hostname}` = the tunnel name); the group `MatOS`;
  one rule per record with that source; the CNAME `*.domain` of the tunnel route has `cnameTargets: [tunnel name]` (Matddns writes a CNAME only through a rule
  with a source that has an address; a CNAME is refused on a DynDNS group). A source of another kind is deleted only once no rule uses it. Matddns never deletes
  a record at the provider.

## MatDock (`ghcr.io/real-ttx/matdock`)

MatDock has no API today. New: the key is **`MatDock__Api__Key`**. The API works on the **local environment** (the Docker engine of the host,
through the mounted socket) unless `?environment=<name or id>` says otherwise.

| Method and path | |
|---|---|
| `GET /api/v1/status` | common rules plus `environments: [{id, name, type, status}]` |
| `PUT /api/v1/environments/local` | **ensure** an environment of type *Local* exists (name `local`); answers `{id, name}`. Also done at start when `MatDock__Environments__EnsureLocal=true`. `409` if no Docker socket is available. |
| `GET /api/v1/environments` | the **nodes** (docs/ARCHITECTURE.md "Nodes"): `[{id, name, type: "local"\|"ssh"\|…, host, port, username, description, managedBy, publicKey, status, message, enabled, dockerVersion, lastCheckedAt, reading: {at, cpuPercent, memoryPercent, diskPercent, containersRunning}}]`. `port`, `username`, `managedBy`, `publicKey` (the public half of a key MatDock generated, never the private key) and `message` came with apiVersion 8 (MatDock branch `feature/nodes-api`) |
| `PUT /api/v1/environments/ssh/{name}` | create or change an SSH environment `{host, port, username, generateKey, managedBy}` (apiVersion 3; `managedBy` on create only, apiVersion 8): without a key MatDock generates one and answers `{id, name, created, publicKey, connected, status, dockerVersion, message}`. MatOS never sends a private key |
| `POST /api/v1/environments/{id}/test` | connect again: `{connected, status, dockerVersion, hostKey, message}`; the host key is pinned on the first success |
| `DELETE /api/v1/environments/{id}?managedBy=matos` | apiVersion 8: `204`; `409` for the local environment, while MatDock has stacks or schedules there, or when the mark is another one |
| `GET /api/v1/stacks?managedBy=` | every stack of the environment (managed and discovered): `{name, environmentId, managed, managedBy, state: "running"\|"stopped"\|"partial"\|"unhealthy"\|"missing", containers: [{id, name, service, image, state, status, ports}], updatedAt}` |
| `GET /api/v1/stacks/{name}` | the same plus `composeYaml` and `envContent` |
| `PUT /api/v1/stacks/{name}` | **upsert** a managed stack. Body `{composeYaml, envContent, managedBy, deploy: bool, pull: bool}`. Name rule as MatDock's own (`^[a-z0-9][a-z0-9_-]{0,62}$`). `deploy:false` = save only (`200 {stack}`); `deploy:true` = save and `docker compose up -d` (with `pull` first if asked), `202 {stack, operationId}`. |
| `POST /api/v1/stacks/{name}/actions/{action}` | `action` = `start` \| `stop` \| `restart` \| `pull` \| `redeploy` \| `update`. `update` = pull, re-create only if an image changed, body `{backupFirst: bool}` (a bundle backup first, abort if it fails); the operation's `result` is `{"changed": bool}`. `202 {operationId}` |
| `DELETE /api/v1/stacks/{name}?volumes=false` | `docker compose down` (with `--volumes` if asked), then the stack is removed from MatDock. `202 {operationId}` |
| `GET /api/v1/stacks/{name}/logs?service=&tail=300` | `{"text": "..."}` |
| `GET /api/v1/containers?maxAge=3` | every container of the host (the Task Manager): `{id, name, image, state, status, stack, service, ports, cpuPercent (of one core), cpuOfHostPercent, hostCores, memoryPercent, memoryBytes, netRxBytes, netTxBytes, blockReadBytes, blockWriteBytes}`; the I/O are totals since the container started; `maxAge` (3-30 s) is how old MatDock's shared `docker stats` may be. The I/O, the share of the host and `maxAge` came with apiVersion 6 (MatDock `dev`, 2026-11-27); MatOS reads an older answer too. |
| `GET /api/v1/host` | a live reading of the host, at most three seconds old (apiVersion 6): `{cores, cpuPercent, load1, memoryTotalBytes, memoryUsedBytes, memoryPercent, diskTotalBytes, diskUsedBytes, diskPercent, uptimeSeconds, containersRunning, dockerVersion, at}`; an older MatDock answers 404 and MatOS uses the reading of `GET /api/v1/environments` |
| `POST /api/v1/containers/{name}/actions/{action}`, `GET /api/v1/containers/{name}/logs?tail=` | start, stop, restart one container; its log as text |
| `GET /api/v1/operations/{id}?offset=` | the operation, see the common rules |

The operating system of this computer (`apiVersion` 7, MatDock branch `feature/host-updates-api`; MatOS's side: docs/ARCHITECTURE.md "The updates of this computer",
`MatDockClient`, `Core/Updates/HostUpdates.cs`). An older MatDock answers `404`: MatOS then asks for an update of the engines.

| Method and path | |
|---|---|
| `GET /api/v1/host/updates` | what MatDock's last check of the host found, asks the host nothing: `{environmentId, environment, supported, checkedAt, os, apt, listsUpdatedAt, listsStale, rebootRequired, pending, security, dockerVersion, dockerTarget, summary, error, packages[], lastRun{unit, scope, startedAt, finished, exitCode, finishedAt}, rebootRequestedAt}`; `checkedAt: null` before the first check (MatDock looks every six hours, three minutes after its start) |
| `POST /api/v1/host/updates/check` | refresh the package lists and look again. `202 {operationId}`, the result is the same view |
| `POST /api/v1/host/updates/apply` | body `{scope: "all"\|"docker"}`: `apt-get upgrade --with-new-pkgs` of every package (nothing removed, configuration kept), started at once on the host's systemd. `202 {operationId, unit}`, result `{unit, exitCode, rebootRequired, summary}`; `409` before a check, without apt, or while one runs |
| `GET /api/v1/host/updates/runs/{unit}` | `{unit, finished, exitCode, log}` read from the host: the end of an upgrade after Docker, MatDock and MatOS restarted |
| `POST /api/v1/host/reboot` | body `{confirm: "reboot"}` (else `400`): the host restarts in 15 seconds. `202 {environment, restartsAt}`; `409` while an upgrade runs |

Backups (a stack bundle: all volumes + compose + env + image references; MatDock's existing bundle backup):

| Method and path | |
|---|---|
| `POST /api/v1/stacks/{name}/backups` | body `{stopContainers: bool, note: string?, targetId: number?}` (target = the local target by default). `202 {operationId}`, the `result` holds `{"backupId": ...}` |
| `GET /api/v1/backups?stack=` | `[{id, stack, createdAt, sizeBytes, volumeCount, consistent, kind: "manual"\|"scheduled"\|"preUpdate", note, status: "succeeded"\|"failed"\|"running", targetId}]`, newest first |
| `POST /api/v1/backups/{id}/restore` | body `{backupCurrentFirst: bool, environment?: "<id or name>", volumesOnly?: bool}`, recreates the stack if it no longer exists. `environment` restores into another environment (the stack moves there), `volumesOnly` restores only the volumes and leaves the stack to MatOS (both apiVersion 8; MatOS moves an app this way). A volume that is not there yet comes back with the compose labels of its stack, so the removal of the stack with its volumes takes it too. `202 {operationId}` |
| `DELETE /api/v1/backups/{id}` | `204` |
| `GET /api/v1/backups/{id}/download` | the bundle as a `.tar` stream |
| `GET /api/v1/backup-schedules`, `PUT /api/v1/backup-schedules/{name}`, `DELETE /api/v1/backup-schedules/{name}` | a **bundle** schedule: `{stack: string\|null, managedBy, frequency: "daily"\|"weekly", time: "03:00", weekday: "Sunday", retention: 7, stopContainers: true, enabled: true}`. `stack: null` = every stack whose `managedBy` equals the schedule's. Retention keeps the newest *scheduled* bundles per stack. Shows up in MatDock's Schedules page with the badge. |

Backup targets (apiVersion 5, branch `feature/backup-targets-api`; where a bundle is kept besides MatDock's data volume, which is the implicit target `null`):

| Endpoint | Contract |
|---|---|
| `GET /api/v1/backup-targets`, `GET /api/v1/backup-targets/{id}` | `[{id, name, type: "smb"|"webdav"|"sftp"|"restic", isDefault, managedBy, smbHost, smbShare, smbDirectory, smbUsername, smbDomain, hasSmbPassword, webDavUrl, webDavUsername, hasWebDavPassword, sftpHost, sftpPort, sftpDirectory, sftpUsername, hasSftpPassword, hasSftpPrivateKey, sftpHostKey, resticRepository (redacted), hasResticPassword, backupCount, schedules: [name]}]`. A password or key is **never** returned, only `has…` |
| `POST /api/v1/backup-targets` | the fields above plus `smbPassword`, `webDavPassword`, `sftpPassword`, `sftpPrivateKey` (OpenSSH or PEM, no passphrase), `resticPassword`, `resticEnv`; `managedBy` is set on create only. `201` with the target, `400 {error}` with the reason |
| `PUT /api/v1/backup-targets/{id}` | the same; a blank or missing secret keeps the stored one, the `type` cannot change (`400`), `resetSftpHostKey: true` forgets the saved host key; another `sftpHost`/`sftpPort` forgets it too |
| `DELETE /api/v1/backup-targets/{id}` | `204`; `409 {error}` while bundles or volume backups are kept there or a schedule writes to it (the reason names them) |
| `POST /api/v1/backup-targets/{id}/test` | writes and deletes a test file: `{ok, message, sftpHostKey}`; the first success of an SFTP target saves the server's host key (trust on first use), a different key later is refused |
| `POST /api/v1/backup-targets/test` | the same for unsaved input (the body of `POST`); `id` fills blank secrets from that target. Always `200 {ok, message}` |

`targetId` on `POST /stacks/{name}/backups` and on a bundle schedule chooses the target; `GET /backups` answers `targetId` and `targetName` per bundle.
A restore reads the bundle from the target it was written to. MatOS only changes and deletes targets with its mark (`managedBy: matos` or `mattiverse`); the others can be chosen.

The compose text that MatOS sends carries the block `x-matdock` (name, description, category) that MatDock's launchpad already understands, so the
stack appears there as an app tile.

What was built, and where it differs from the sketch above (branch `mattiverse-integration`):

- **Schedule times are UTC** (MatDock's schedules run in UTC); MatOS says so on the schedule form. `stack: null` backs up every stack whose `managedBy`
  matches the schedule's, or every managed stack when the schedule has none. `retention` keeps the newest *scheduled* bundles per stack of that schedule and drops
  failed attempts that a newer success replaced; `0` is unlimited.
- `DELETE` works on stacks MatDock manages only (`404` otherwise); on a stack it does not manage only `start`, `stop` and `restart` are allowed (`409` for the rest).
  `pull: true` without `deploy: true` is a `400`. `state` can be `"unknown"` when Docker does not answer (the list endpoint answers `502`).
- Stacks and `GET /backups` are limited to the chosen environment (`?environment=<id|name>`, default the local one); `GET /backup-schedules` lists all schedules (with `environmentId`), and `PUT /backup-schedules/{name}?environment=` puts one into a node. MatOS calls every endpoint of an app on another node with `?environment=<id>` (`MatDockClient.At`), and keeps a copy `<name>-node<id>` of a schedule for all apps on every node with apps (MatDock runs a schedule in one environment).
- A restore **re-creates a stack that was deleted** (compose, `.env`, volumes), which is how an uninstalled app comes back; MatOS then takes the stack
  back as an app (`AppReconciler`) and publishes its route and record again.
- The download is a `.tar` holding the manifest and one tar per volume. Extra fields (`created`, `enabled`, `lastStatus`, `cron`, `nextRunAt`, `safetyBackupId`, ...) are returned and ignored;
  `frequency` reads back as `custom` when the cron was edited in MatDock's UI.
- The `kind` of a backup (`manual`, `scheduled`, `preUpdate`) is chosen by MatDock; MatOS's own pre-update and pre-restore backups carry a note and show as manual.

## MatIdentity (`ghcr.io/real-ttx/matidentity`)

The single sign-on of the family (MatDesign docs/PLATFORM.md, "Sign-in with MatIdentity"). Key: `MAT_API_KEY` (the key of its platform `/api`, also the key of its `/api/v1`).
`PUT /api/v1/clients/{clientId}` (`displayName`, `homeUrl`, `redirectUris`, `postLogoutRedirectUris`, `allowSignIn`, `allowMachine`, `callsAllApps`, `managedBy`, `renewSecret`,
`backchannelLogoutUri`) → `clientSecret` only for a new client or a renewed one; `DELETE /api/v1/clients/{clientId}?managedBy=matos`. MatOS sets `MATIDENTITY_ISSUER` (its public address) and registers
**itself** this way (`IdentityLink`, docs/ARCHITECTURE.md "MatIdentity, the single sign-on"). **The apps** are bindings of `identity.oidc` (MatDesign docs/PLATFORM.md):
`PUT /api/bindings/identity.oidc/<slug>` with `MAT_API_KEY` (the consumer's addresses, its internal address, the params `callback`, `signedOut`, `backchannel`) → the four
`MATIDENTITY_*` variables; `DELETE /api/bindings/identity.oidc/<slug>?managedBy=matos`. MatIdentity makes the same client as `/api/v1/clients` would.
`backchannelLogoutUri` is where MatIdentity posts its logout tokens (OpenID Connect Back-Channel Logout 1.0: form field `logout_token`, a JWT of type `logout+jwt` with
`iss`, `aud`, `iat`, `exp`, `jti`, `events`, `sub` and, unless the person was signed out everywhere, `sid`; five seconds, one more try). MatOS always sends it: the app's
address on the shared network (`http://<container>:<port>/signout-backchannel`), MatOS's own (`http://<its container>:<its port>/signout-backchannel`), or `""` (removes
it) when there is none; a missing field would leave what MatIdentity has.

**Branded sign-in** (MatIdentity docs/ARCHITECTURE.md "Branded sign-in"; here docs/ARCHITECTURE.md "MatOS's sign-in looks like MatOS"). The same PUT takes `branding`:
`{ name (1–60), accent: "#rrggbb"?, hideIdentity: bool, logo: { contentType: "image/svg+xml"|"image/png", data: base64 }?, background: { contentType: "image/jpeg"|"image/png"|"image/webp", data: base64 }? }`.
A missing `branding` keeps it, `null` removes it; inside it `name`, `accent` and `hideIdentity` are replaced together, a missing `logo`/`background` keeps the stored picture and
`null` removes it. Limits: logo ≤ 256 KiB, background ≤ 2 MiB, the bytes must match the type; anything wrong is `400 { errors: { "branding.*": message } }` and nothing is
saved. Only the client's manager brands it: `managedBy` must be the client's mark, else `409`. `GET /api/v1/clients[/{id}]` answers
`branding: { name, accent, hideIdentity, hasLogo, hasBackground, logoContentType, backgroundContentType, logoUrl, backgroundUrl }` or `null`, never the data; the URLs are
absolute with `?v=<first 16 hex digits of the SHA-256 of the bytes>`. MatIdentity serves them anonymously from its own origin (`/branding/{clientId}/logo`, `/background`,
`/icon.svg`, `/theme.css`; strong ETag, a year of `immutable` caching with the current `?v`, `nosniff`, a sandboxing CSP for the pictures). When a sign-in belongs to a branded
client (first match: the `client_id` of the local `/connect/authorize` or `/connect/logout` request in `returnUrl`, which always wins over a `?brand=` beside it, the
OpenID Connect request an error page answers, `?brand=`, or the cookie `mid.brand`, 30 minutes) its pages (Login, Forgot, Reset, TwoFactor, Register, Verify, NoAccess,
AccessDenied, ChangePassword (the forced change of a password), the sign-out question Logout, and the error pages StatusCode and Error) show the client's logo, name ("Sign in to MatOS"), accent, background, title and icon; with `hideIdentity` nothing of MatIdentity. The reset and
verify mails carry `&brand=` and, with `hideIdentity`, the client's name. A broker names its brand for the mails it triggers with the header `X-Mat-Brand: <clientId>` on
`POST /api/v1/people/{subject}/actions/invite|resetPassword` and SCIM `POST /scim/v2/Users` (an id that is no branded client is ignored); MatOS sends its own client id
on every write of the People area (`MatIdentityPeople.BrandHeader`). MatIdentity's mail goes out as `account@<sender domain>` (the catalog's `mail.smtp` param `sender`),
not `matidentity@`. **MatOS** sends `{ name: <instance name>, accent: "#8558ec", hideIdentity: true, logo: img/logo.svg,
background: img/wallpapers/orbit-light.jpg }` with `managedBy: "matos"` and nothing else (the rest of the client stays), only when the client's `GET` has the field `branding`
(an older MatIdentity has not; the status stays `apiVersion: 1`) and only what differs (`IdentityLink.BrandSelfAsync`, `MatIdentityClient.BrandAsync`). MatOS's sign-out
sends `id_token_hint`, so MatIdentity's `/connect/logout` ends the session without asking and returns to `/signout-callback-oidc`. MatOS keeps the id token in
its session cookie whenever it writes the cookie again (theme, wallpaper, password: `SessionCookie.RefreshAsync`); without a hint the question is asked in MatOS's look.

**A person's own second step and password** (docs/ARCHITECTURE.md "The second step"). MatOS has no API call for them: the account tabs Security and Password link
two pages of MatIdentity below its public address (the `authority` of the sign-in), `/Account/Security?brand=<clientId>` (authenticator app, recovery codes, passkeys)
and `/Account/Profile?tab=password&brand=<clientId>`, opened in a new tab (`Core/Users/AccountSecurity`). They are MatIdentity's account pages, and its session lets
the person in; `brand` (MatOS's own client id, the brand it set) shows them in MatOS's look, without MatIdentity's menu and, with `hideIdentity`, without its name
(MatIdentity docs/ARCHITECTURE.md "Branded sign-in", "The account from a link of the app"; on its `dev` since 2026-11-27). The account pages take a brand only from that
`?brand`, never from the cookie of a sign-in; a MatIdentity without that change, or a client without a brand, shows its own account. MatIdentity says nothing about whether a person's second step is on
(neither SCIM nor `/api/v1`), so MatOS does not show it; an administrator resets it with the action `resetSecondStep`.

## MatSMTP (`ghcr.io/real-ttx/matsmtp`)

The mail relay of the family (MatDesign docs/PLATFORM.md, "Mail through MatSMTP"). Image tags `latest` and `release` from `main`, `nightly` from `dev`. In the container: web **2525**,
SMTP **2025** (STARTTLS), submission **2587**. The catalog publishes only the submission port (`SUBMISSION_PORT`, default 2587) for devices in the network; the apps hand in their
mail on the shared network and **relay users may authenticate on the SMTP port from the Docker network without TLS**.

Environment: **`MATSMTP_API_KEY`** (the key of `/api/v1`; generated, hidden), `MATSMTP_ADMIN_PASSWORD` (at least 8 characters; seeds the administrator, so no first-run page is needed),
`MAT_API_KEY` and the `MATIDENTITY_*` variables (it is a platform app and consumes `identity.oidc`). Volume `matsmtp-data:/data`.

| Call | Body / answer |
|---|---|
| `GET /api/v1/status` | `{"app":"matsmtp","version":"…","apiVersion":1,"smtpPort":2025,"smtpTls":"starttls"}` (`none`, `starttls` or `tls`): where the apps hand in their mail |
| `PUT /api/v1/relay-users/{id}` | `{"displayName","allowedSenders":["matbu@example.com"],"managedBy":"matos","renewSecret":bool}` → `{"id","username","password","created":bool}`; `password` only when the user was created or `renewSecret` was set |
| `GET /api/v1/relay-users` | the relay users (`managedBy` with each) |
| `DELETE /api/v1/relay-users/{id}?managedBy=matos` | `204`; `404` when it does not exist; `409` when it is not managed by MatOS (it stays) |
| `GET`/`PUT /api/v1/settings` | `{"setupCompleted":bool,"defaultSenderDomain":"example.com"}` |

What MatOS does (`MatSmtpClient`, `MatSmtpProvisioner`, `MailLink` for the setup; the broker for the apps):

- **After the install** (`provision: matsmtp`): waits for the API, sets `setupCompleted: true` and `defaultSenderDomain` = the domain of the wizard (when there is one; otherwise
  MatSMTP keeps its own), then binds every app that consumes `mail.smtp` and deploys it again. The account MatSMTP delivers through is set in MatSMTP's own UI.
- **Every install and update of an app that consumes `mail.smtp`:** a binding, `PUT /api/bindings/mail.smtp/<slug>` with `MAT_API_KEY` (the param `sender`) → the six
  `MATSMTP_*` variables (MatSMTP's container on the shared network, its port and TLS mode, the relay user, the password once, `<sender>@<defaultSenderDomain>`). MatOS keeps
  the password and asks with `renew` only when it has none. Not installed: the variables are emptied and the app sends its mail itself. `/api/v1/relay-users` stays for the rest.
- **Uninstalling an app** removes its binding (the relay user). **MatSMTP comes or goes:** every app that consumes `mail.smtp` is bound again (or loses it) and redeployed.
  **Connect again** (Settings, Engines) and a new domain in the wizard set the domain of the senders again and bind the apps again.

## What MatOS does with them

- **Installing an app:** renders the catalog entry to one compose file and a `.env`, then `PUT /stacks/matos-<app>` (MatDock), and the broker binds what it consumes:
  with a domain its route (`PUT /api/bindings/web.route/<slug>` at Matcad, the param `host`; `/api/v1/routes` for an older Matcad), its sign-in and its mail; then the DNS
  records (Matddns). Uninstalling removes all of it.
- **Without the engine API** (an older released image, or the engine is not installed yet) MatOS falls back to its own compose
  runner for the stack, so nothing stops working; the settings page says which engines are connected.
- **The wizard** installs the five engines first (MatDock through MatOS's own compose runner, because nothing can deploy MatDock before
  it exists; Matcad, Matddns, MatIdentity and MatSMTP then as MatDock stacks), hands each the API key it generated, and asks once for the domain and the DNS provider, which
  goes to Matcad (certificates) and Matddns (records).
